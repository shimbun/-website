## 0. 計測設計の基本方針

| # | 方針 | 理由 |
|---|------|------|
| 1 | **頂点は「相談予約数」**、次点「問い合わせ数」。PV やユーザー数はあくまで途中指標 | ブリーフの最重要KPIが相談獲得のため |
| 2 | イベントは **少数・命名統一・パラメータで切る**（`cta_click` 1種類を `cta_location` で分解する等） | 小規模サイトで運用者が迷わない。GA4のカスタムディメンション上限（イベントスコープ50）にも余裕を残す |
| 3 | **個人情報（氏名・メール・電話・自由記述・子の学校名等）は一切 GA4 / Clarity に送らない** | 利用規約・法令順守、ブランドの「誠実」 |
| 4 | スマホ最優先で分析（デバイス別を常にデフォルトで見る） | 絶対ルール6 |
| 5 | 小規模サイト前提で「統計的に有意なABテスト」に固執せず、定性（ヒートマップ・録画・相談時ヒアリング）と組み合わせる | 流入量が少ない想定のため（§7） |
| 6 | 計測の「正しさ」を公開前にQAし、公開後もイベント件数の急変を監視する | 計測漏れは改善サイクル全体を壊す |

## 1. KGI / KPI ツリー

### 1-1. ツリー（相談予約数を頂点に分解）

```
【KGI】月間 相談予約数（予約完了件数）
│
├─ ① サイト訪問セッション数（量）
│   ├─ 自然検索（Organic Search）
│   │   ├─ 表示回数（Search Console impressions）
│   │   ├─ 平均掲載順位
│   │   └─ CTR（検索結果クリック率）
│   ├─ SNS（Instagram / X / YouTube 等 ※運用有無は要確認）
│   ├─ LINE配信からの再訪
│   ├─ 広告（Google / Meta 等 ※実施有無は要確認）
│   ├─ 指名検索（「COMPASS 中学受験」等）＝認知の代理指標
│   └─ 紹介・参照（Referral）/ Direct
│
├─ ② 検討深化率（質）
│   ├─ エンゲージメント率（GA4 engaged sessions / sessions）
│   ├─ 重要ページ到達率
│   │   ├─ 料金ページ閲覧率（pricing_view）
│   │   ├─ サービス詳細閲覧率
│   │   ├─ 支援事例・お客様の声 閲覧率
│   │   └─ コンサルタント紹介 閲覧率
│   ├─ スクロール深度（TOP 50%/75%/90% 到達率）
│   ├─ FAQ開閉数（faq_open）＝不安の所在
│   └─ 平均エンゲージメント時間
│
├─ ③ CTA反応率
│   ├─ CTAクリック率（cta_click / sessions）… 位置別：FV・中間・料金下・最終CTA・追従ボタン
│   └─ LINEクリック率（line_click / sessions）
│
└─ ④ フォーム完了率（転換）
    ├─ 予約ページ到達 → フォーム開始率（form_start / 予約ページ閲覧）
    ├─ フォーム開始 → 送信完了率（form_submit / form_start）
    ├─ フォームエラー発生率（form_error）
    └─ 予約完了（booking_complete / generate_lead）

【サブKGI】問い合わせ件数（contact フォーム送信）
【先行指標】LINE友だち追加数（LINE公式アカウント側の数値と突合）
【事業KPI（サイト外・参考）】相談 → 継続コンサル成約率 ※CRM/手集計。GA4には個人単位で連携しない
```

### 1-2. 数式としての分解

```
相談予約数 ＝ セッション数 × 予約ページ到達率 × フォーム開始率 × フォーム完了率
CVR（セッション基準）＝ 相談予約数 ÷ セッション数
総合CV ＝ 相談予約 ＋ 問い合わせ （＋ LINE友だち追加 を「マイクロCV」として別集計）
```

| サブKGI | 問い合わせ数 | `generate_lead`（lead_type=contact）件数 | 同上 | 週次 |

## 2. GA4 イベント設計

### 2-1. プロパティ基本設定

| 項目 | 設定 |
|---|---|
| プロパティ | 1サイト1プロパティ、Webデータストリーム1本 |
| タイムゾーン / 通貨 | 日本 / JPY |
| データ保持期間 | **14か月**（デフォルト2か月から変更必須） |
| 拡張計測 | page_view ON、scroll **OFF**（独自に25/50/75/90%で実装するため）、outbound click ON、site search ON（検索機能がある場合）、**form interactions OFF**（独自イベントと重複・誤発火を避ける）、video engagement はYouTube埋め込みがあればON |
| 内部トラフィック除外 | 運営者・制作会社のIPを「internal」定義 → テスト期間は「テスト」状態、公開後「有効」 |
| 開発トラフィック | ステージング環境は別プロパティまたは `debug_mode` で分離 |
| 除外する参照元（Unwanted referrals） | 外部予約システム・決済サービスのドメイン（例：予約ツールを外部SaaSにする場合） |
| クロスドメイン | 予約フォームが別ドメインの場合のみ設定（§10 確認事項） |
| Googleシグナル | 原則 OFF（小規模サイトでしきい値適用によるデータ欠落を避ける） |
| レポート用識別子 | 「デバイスベース」または「ブレンド」※しきい値によるデータ非表示が出たらデバイスベースへ |
| Search Console リンク | 有効化 |
| Google 広告リンク | 広告を実施する場合のみ |
| BigQuery エクスポート | 初期は不要。データ量増加後・高度分析時に検討（無料枠あり） |

### 2-3. キーイベント（CV）定義

| 区分 | イベント | 扱い | カウント方法 |
|---|---|---|---|
| **メインCV** | `generate_lead`（lead_type=booking） | キーイベント | 「セッションごとに1回」 |
| **メインCV** | `generate_lead`（lead_type=contact） | 同上（同イベント内でlead_typeで分離） | 同上 |
| マイクロCV | `line_click` | キーイベントに **登録するかは要判断**。登録する場合も「メインCVとは別の指標」としてレポート上分離 | セッションごとに1回 |
| マイクロCV | `tel_click` | 同上 | 同上 |
| 中間指標 | `cta_click`, `form_start` | キーイベントにしない（CV数が水増しされ、広告最適化を歪めるため） | — |

- GA4ではキーイベントに「lead_type 別」の条件付き定義ができないため、**`generate_lead` を1つのキーイベントとし、レポートで `lead_type` 別に分解**する。予約だけを独立のキーイベントで見たい場合は、GA4の「イベントを作成」機能で `booking_lead`（generate_lead かつ lead_type=booking）を派生させる。
- 広告を実施する場合、Google 広告にインポートするのは **予約（booking）のみ** を原則とする（LINEクリックを入れると入札が「クリックされやすいが成約しない」方向へ最適化されやすい）。
- 外部予約ツールで完了ページにタグを置けない場合、「予約ツールへの遷移クリック（`cta_click` のうち link_url が予約ツール）」を暫定CVとし、予約ツール側の実数と週次で突合する。

## 3. GTM（Google Tag Manager）構成案

### 3-1. 全体方針

- **GTM 1コンテナ（Web）**で GA4・Clarity・（将来）広告タグを一元管理。サイトHTMLに直書きするのは GTM スニペットのみ。
- イベントは **dataLayer.push 方式を基本**（実装側が `event` と上記パラメータを push、GTMはそれを受けて GA4 に送る）。CSSセレクタ依存のクリックトリガーはデザイン変更で壊れやすいため補助的に留める。
- クリック系要素にはデータ属性を付与する仕様とする（例：`data-cta-location="fv"`、`data-cta-text="中学受験について相談する"`）。実装担当（技術設計Agent）へ仕様として引き渡す。
- 公開：ワークスペースでプレビュー → GA4 DebugView で確認 → バージョン名・説明を付けて公開。

### 3-2. dataLayer 仕様（イベント名一覧＝§2-2と同一）

| dataLayer `event` 値 | 必須キー |
|---|---|
| `cta_click` | `cta_location`, `cta_text`, `cta_variant`, `link_url` |
| `line_click` | `cta_location`, `cta_text` |
| `form_start` / `form_step` / `form_error` / `form_submit` | `form_id`（＋各パラメータ） |
| `generate_lead` | `lead_type`, `form_id` |
| `faq_open` | `faq_id`, `faq_category` |
| `section_view` | `section_id` |
| `exp_assign` | `exp_id`, `exp_variant`（ABテスト割付時） |

全ページ共通でページ読込時に push：`page_type`, `content_group`, `consent_state`（granted/denied）。

- 変更履歴を本書末尾または別シートの「計測変更ログ」に記録（ABテスト開始/終了もここに記録）。

### 3-5. UTM 命名規則

**原則**：すべて英小文字、スペース不可（区切りは `_`）、日本語不可、`utm_source` / `utm_medium` / `utm_campaign` は必須、`utm_content` は任意（クリエイティブ・位置の識別）、`utm_term` は検索広告のみ。GA4のデフォルトチャネルに正しく振り分けられる medium を使う。

| 流入 | utm_source | utm_medium | utm_campaign 例 | utm_content 例 |
|---|---|---|---|---|
| Instagram 投稿/プロフィールリンク | `instagram` | `social` | `profile` / `post_2026-10_juku_select` | `bio_link` / `story_01` |
| X（旧Twitter） | `x` | `social` | `post_2026-10_school_select` | `thread_01` |
| YouTube 概要欄 | `youtube` | `social` | `video_2026-10_study_plan` | `description` / `pinned_comment` |
| note 等ブログ | `note` | `referral` | `article_2026-10_transfer` | `end_link` |
| **LINE 配信（一斉）** | `line` | `line_message`※ | `broadcast_2026-10-15_mock_exam` | `rich_message` / `text_link` |
| **LINE リッチメニュー** | `line` | `line_richmenu`※ | `richmenu` | `booking` / `pricing` |
| LINE ステップ配信 | `line` | `line_step`※ | `step_day03_service_intro` | `text_link` |
| Google 検索広告 | `google` | `cpc` | `search_brand` / `search_generic_juku` | 広告グループ略称 |
| Meta 広告（Instagram/Facebook） | `meta` | `paid_social` | `2026-10_awareness_worries` | `creative_a` / `creative_b` |
| YouTube 広告 | `youtube` | `paid_video` | `2026-11_brand` | `15s_a` |
| メール（メルマガ等） | `newsletter` | `email` | `2026-10_monthly` | `header_link` |
| QR（チラシ・名刺・セミナー） | `flyer` / `seminar` / `card` | `offline` | `2026-10_seminar_tokyo` | `qr_front` |
| 提携・紹介サイト | 提携先名 | `referral` | `partner_2026` | — |

※LINE の medium はGA4デフォルトチャネルでは「Unassigned」になりうるため、**GA4の「チャネルグループ」にカスタムチャネル「LINE」（source=line）を作成**して集計する。

- Google 広告は **自動タグ設定（gclid）を優先** し、UTMは手動併用する場合も値を上表で統一。
- campaign の日付は `YYYY-MM` または `YYYY-MM-DD` 形式で統一。
- **UTM管理シート**（URL・発行日・担当・配信先・完成URL）を運用し、手打ちを禁止（生成用テンプレートで作成）。
- サイト内リンクには UTM を付けない（セッションが分断されるため）。

### 4-2. クエリ分析の方針

| 分析 | 見方 | アクション |
|---|---|---|
| 指名 vs 一般 | クエリに「compass / コンパス」を含むかで分類（Looker Studioで正規表現分類） | 指名の伸び＝認知施策の成果。一般クエリ＝コラム・SEOの成果 |
| 意図別分類 | 塾選び・転塾・志望校・併願・成績・家庭学習・模試・過去問・相談先 等のテーマ別にクエリをグルーピング | どの悩みテーマから流入・CVしているかをGA4ランディングページと突合 |
| 伸びしろクエリ | 掲載順位 **8〜20位** かつ表示回数が多いクエリ | 該当ページのリライト（見出し・網羅性・内部リンク強化） |
| 新規クエリ | 前月になかったクエリ | 新コラムのテーマ候補 |
| カニバリ | 同一クエリで複数ページが入れ替わり表示 | 主ページを決め、内部リンク・統合を検討 |

### 4-3. CTR 改善方針

1. **対象抽出**：表示回数が多い（上位20%）のに、CTRが同順位帯の平均より低いページ・クエリ。
2. **改善**：title / meta description を検索意図に合わせて修正（例：「塾選び 相談」なら「第三者の立場で塾選びを整理」など）。**「絶対合格」「必ず伸びる」等の煽り表現・誇大表現は使わない**（ブランドルール）。料金を明記している強みはスニペットで訴求可。
3. **検証**：変更日をログに記録し、変更前後 **4週間** の CTR・順位を比較（順位変動の影響を分けるため、同程度の順位帯で比較）。
4. 検索順位は短期で揺れるため、週次は傾向確認のみ、判断は月次。

## 7. ABテスト計画

### 7-1. 前提：小規模サイトでのテスト現実性（重要な注意）

- 相談予約のように **CV数が月数件〜数十件** のサイトでは、「予約数」を指標にした統計的に有意なABテストは **数か月〜1年以上** かかり、現実的でないことが多い。
- そのため：
  1. **判定指標は上流のマイクロ指標**（CTAクリック率、予約ページ到達率、フォーム開始率）を主指標とし、予約数は「悪化していないか」のガードレール指標とする。
  2. 差が大きく出やすい **大胆な変更**（FV全体、ページ構成）から試す。ボタン色などの微差テストは後回し。
  3. 流入が足りない場合は **前後比較（期間比較）＋ヒートマップ・録画＋相談時ヒアリング** の定性評価で判断する（季節変動・流入元構成の変化に注意して解釈）。
  4. 同時に複数テストを走らせない（同一ページ）。
  5. **途中で結果を覗いて早期終了しない**（事前に期間とサンプル数を決め、最低2週間＝曜日効果を含む期間を確保）。
- ツール：Google Optimize は2023年に終了済み。候補は VWO / Optimizely / AB Tasty 等の有償ツール、または **実装側でパターンをランダム割付し `exp_variant` をGA4に送る方式**（小規模なら後者が低コスト）。表示のちらつき（フリッカー）とSEO（canonical・クローラーへの同一コンテンツ提供）に留意。

### 7-2. 必要サンプル数の考え方

2群比較（有意水準5%・検出力80%）の簡易目安：

```
1群あたり必要サンプル数 n ≒ 16 × p × (1 − p) ÷ Δ²
  p：ベースラインの率（例：CTAクリック率）
  Δ：検出したい差（絶対値）
```

| 主指標 | ベースライン p（仮） | 検出したい改善 | Δ | 1群あたり n（概算） | 2群合計 |
|---|---|---|---|---|---|
| 予約CVR | 1.0% | 相対+30%（→1.3%） | 0.3pt | 約17,600セッション | 約35,000 |
| 予約CVR | 1.0% | 相対+50%（→1.5%） | 0.5pt | 約6,300 | 約12,700 |
| CTAクリック率 | 10% | 相対+20%（→12%） | 2pt | 約3,600 | 約7,200 |
| CTAクリック率 | 10% | 相対+30%（→13%） | 3pt | 約1,600 | 約3,200 |
| フォーム完了率 | 50%（form_start基準） | +10pt（→60%） | 10pt | 約400 form_start | 約800 |

- **必要期間 ＝ 2群合計サンプル数 ÷ テスト対象ページの週間セッション数**。例：TOPが週1,000セッションなら、CTAクリック率+30%検出に約3〜4週、予約CVR+30%検出には約35週 → 予約CVRでの判定は非現実的。
- 実測ベースライン確定後、この表を再計算してテスト可否を判断する（判定ルール：必要期間が **8週以内** のテストのみ実施。超える場合は前後比較で代替）。

- **テストせずに直すもの**（明確な不具合・ユーザビリティ問題）：タップ領域が小さい、フォームのエラー表示が分かりにくい、読み込みが遅い、リンク切れ等 → 即修正。
- 表現面の制約：どのパターンもブランドルール（合格保証・煽り・誇大実績の禁止、「無料相談」表記の条件）を満たすこと。コピー案は Agent（コピー担当）と調整。

## 8. ヒートマップ・行動分析ツールの導入検討

### 8-1. 比較

| ツール | 費用 | 主機能 | 評価 |
|---|---|---|---|
| **Microsoft Clarity** | 無料（PV上限なし） | ヒートマップ（クリック・スクロール）、セッション録画、デッドクリック・レイジクリック検出、GA4連携 | **第一推奨**。小規模サイトに最適。テキストマスクが標準で有効 |
| Hotjar | 無料枠あり（録画数制限）／有料 | ヒートマップ、録画、アンケート | アンケート機能が必要なら候補 |
| ミエルカヒートマップ / User Heat 等（国産） | 無料枠〜有料 | 日本語サポート、熟読エリア | 国産サポート重視なら候補 |

### 8-2. Clarity 導入方針

- GTM経由で設置（§3-3）。GA4とのプロジェクト連携を有効化。
- **マスキング設定は「厳格（Strict）」**：全テキスト・入力値をマスク。最低限、**フォーム入力欄は必ずマスク**（標準で入力値はマスクされるが、設定・確認必須）。予約フォーム・問い合わせフォームのページは、録画対象から除外するか厳格マスクを確認のうえ運用。
- カスタムタグ：`page_type`、`exp_variant` を付与し、ABパターン別に録画・ヒートマップを見る。
- 活用：
  - TOPのスクロールヒートマップでセクション別離脱を確認（section_view と突合）
  - デッドクリック（リンクでない画像・テキストのタップ）＝ユーザーが期待しているリンク先の発見
  - レイジクリック（連打）＝不具合や反応遅延
  - 料金・FAQ周辺の熟読状況
- 小規模サイトではヒートマップのサンプルが少ないため、**最低でも各ページ数百セッション程度溜まってから** 判断する。録画は件数が少なくても定性的な発見に有効。

## 9. プライバシー配慮

### 9-1. 法令・ルール上の前提（日本）

- **改正電気通信事業法の外部送信規律（2023年6月施行）**：GA4・Clarity・広告タグ等で利用者情報を外部送信する場合、送信先・送信される情報・利用目的の **公表（通知または容易に知り得る状態に置く）** が必要となる可能性が高い → プライバシーポリシー内または独立した「外部送信ポリシー（Cookie ポリシー）」ページで明示する。適用範囲の最終判断は法務確認（§10）。
- **個人情報保護法**：Cookie等の個人関連情報を第三者に提供し、提供先で個人データとして取得されることが想定される場合は本人同意が必要な場合がある。GA4側で個人と紐付けない設計にすることで、この論点を最小化する。
- **ユーザー層への配慮**：対象は保護者だが、相談内容は **子どもの成績・学校・家庭事情という機微な情報** を含む。一般的なサイト以上に慎重に扱う（ブランドの「誠実」に直結）。
- EU/EEA 等からのアクセスを主対象としないが、Google の同意モード（Consent Mode v2）に準拠しておくと将来の広告運用・規制強化にも対応しやすい。

### 9-2. Cookie 同意の方針

| 項目 | 方針（推奨案） |
|---|---|
| 同意バナー | **導入推奨**。スマホで邪魔にならない下部小型バナー（CTA・追従ボタンを隠さない配置をUI担当と調整） |
| 方式 | CMP（同意管理ツール）利用を推奨（例：Google認定CMP、国産CMP等。費用は要確認）。「同意する」「拒否する」「設定」を同等の目立ち方で表示 |
| 同意モード | Consent Mode v2 の **Advanced（高度）** モードを推奨：拒否時はCookieを使わないping のみ送信（GA4側でモデリング補完）。デフォルトは `analytics_storage` / `ad_storage` / `ad_user_data` / `ad_personalization` を地域と方針に応じ設定 |
| Clarity | 同意取得後に発火（Clarity の Consent API に同意状態を連携） |
| 広告タグ | 広告実施時のみ設置し、同意取得後に発火 |
| 同意しない場合への影響 | GA4の計測数が減る（拒否率分）。**ダッシュボードで予約ツール実数と突合し、計測カバー率を把握**する |
| 簡易案（予算・工数を抑える場合） | 同意バナーは設置せず、外部送信ポリシーの公表＋オプトアウト手段（Googleアナリティクス オプトアウト アドオン等の案内）で対応 → 法務判断次第 |

### 9-3. 個人情報を GA4・Clarity に送らないためのルール

1. **フォーム入力値（氏名・メール・電話・住所・子の氏名・学校名・塾名・成績・自由記述）を、イベントパラメータ・URL・ページタイトルに一切含めない。**
2. フォーム送信は **POST**、サンクスページURLに入力値をクエリで付けない（例：`/thanks?email=...` は禁止）。
3. 送信するのは **選択式カテゴリのコード値のみ**（`consult_topic_category=juku_select` 等）。塾名・学校名は選択式であっても送らない（組み合わせで個人推定のリスク）。子の学年帯の送信可否もユーザー確認事項とする。
4. `form_error` は **項目ID名とエラー種別のみ**。
5. GA4 の `user_id` 機能は使わない（会員機能がないため不要）。
6. GA4 の「データの削除リクエスト」手順と、誤送信時の対応フロー（発見→該当パラメータ削除リクエスト→原因修正→記録）を運用マニュアルに記載。
7. GA4 の **データ編集（リダクション）設定** で、メールアドレス形式のデータ・指定クエリパラメータ（email, tel, name, phone 等）を除去する設定を有効化（二重の防御）。
8. Clarity は厳格マスク＋フォームページ扱いの確認（§8-2）。
9. 外部予約ツールを使う場合、そのツールの計測・Cookie・個人情報の取扱いも外部送信ポリシーに記載。
10. Looker Studio・スプレッドシートにも個人情報を持ち込まない（件数のみ）。
